From Mapped Component to Enacted Mechanism

When does a behaviour change technique that is present in a digital intervention become an implemented mechanism in real-world care?

A structural reading of Alice Berry's getUBetter logic-model and intervention-mapping work, focused on the gap between intervention content, user exposure, BCT enactment and implementation context.

Digital health Implementation Logic model Behaviour change techniques COM-B MSK self-management
Evidence chain

The logic model makes intervention content unusually explicit

Berry A, McClellan C, Wanless B, Walsh N. A Tailored App for the Self-management of Musculoskeletal Conditions: Evidencing a Logic Model of Behavior Change. JMIR Formative Research. 2022;6(3):e32669. DOI: 10.2196/32669.

The study used the Behaviour Change Wheel, COM-B, the Behaviour Change Technique Taxonomy and persuasive systems design to map getUBetter's content and functionality. Twenty-five BCTs were identified after iterative mapping, including instruction, self-monitoring, goal setting, prompts, graded tasks, social support and verbal persuasion about capability.

The resulting logic model connects target COM-B domains, intervention functions, BCT groups, digital delivery features and intended outcomes. This is a stronger starting point than describing a digital intervention as a single black box.

target behavioural problem → COM-B / theoretical domain → intervention function → BCT → app feature / persuasive design → intended behavioural or clinical outcome
A second mapping layer

Intervention mapping makes the hypothesised route to physical activity explicit

Berry A, McCabe CS, Muir S, Walsh N. Systematic co-development and testing of a digital behaviour change intervention for osteoarthritis and physical activity: Theoretical mapping and acceptability study. Digital Health. 2023;9:20552076231204425. DOI: 10.1177/20552076231204425.

This study used intervention mapping to move from a logic model of the problem to programme objectives, change objectives and practical intervention content. Self-efficacy and autonomous motivation were selected as important determinants of physical-activity engagement, and BCTs were mapped onto the practical materials intended to influence them.

Both studies therefore solve an important design problem: they show why a component is there and what it is intended to change. They do not, by design, establish that every mapped component is encountered or enacted when the intervention is deployed in routine care.

The implementation gap

“Present in the app” is not the same state as “active in the user”

A BCT can be coded as present because the intervention contains a feature capable of delivering it. But a real-world causal chain contains several additional transitions.

feature present → user reaches feature → content is noticed / understood → BCT is enacted → intended determinant changes → self-management behaviour changes → clinical / activity outcome changes

Failure at any earlier transition prevents later parts of the logic model from being activated. For example, a goal-setting function cannot affect self-regulation if a user never reaches it; a reminder cannot act as a prompt if notifications are disabled or ignored; an exercise video cannot build capability if it is viewed but not attempted.

Working distinction: BCT availability is an intervention-content property. BCT enactment is a participant-level event. They are related but not interchangeable evidence.
Implementation context

Routine-care conditions may determine whether the theoretical mechanism is ever exposed

Alice Berry's current getUBetter implementation programme explicitly examines uptake, app use, clinician implementation, pathway position and the contexts in which the technology works for different people. That creates a bridge between the earlier logic model and real-world mechanism testing.

Implementation conditionPossible effect on the causal chain
Clinician recommendationChanges initial trust, uptake and perceived relevance
Point in the care pathwayChanges whether content arrives when a patient is ready to act
Local service configurationChanges what the app supplements, replaces or redirects toward
Digital access and literacyChanges exposure to interactive features and BCTs
Reminders / promptingChanges repeated exposure and re-engagement

These variables are often classified as implementation context. But if they determine whether the user ever encounters and enacts a mapped BCT, they also sit upstream of the proposed mechanism of action.

A possible logic-model extension

Implementation could be represented as a causal condition for enactment

One option is to extend the conventional content-to-outcome model by inserting exposure and enactment explicitly.

implementation context ↓ feature available → feature encountered → BCT enacted → determinant changed → behaviour changed → outcome implementation context may act at several arrows, not only outside the model

This would make it possible to distinguish at least three explanations for a null outcome: the component was not available as intended; it was available but not meaningfully encountered or enacted; or it was enacted but did not change the hypothesised determinant or behaviour.

The distinction matters particularly for digital interventions because software can record availability and some forms of exposure at high resolution, while still leaving interpretation, enactment and transfer into daily behaviour partly unobserved.

Open methodological question

When does a mapped BCT become an implemented mechanism?

When a digital intervention's logic model maps a feature to a BCT and then to a target determinant, what evidence is needed before that BCT can be treated as an implemented mechanism rather than only an available intervention component? Would you distinguish feature present → feature encountered → BCT recognised or enacted → determinant changed → behaviour changed, and which of those transitions need direct measurement in a real-world implementation study?

A related question is whether clinician recommendation, pathway position, timing and local service configuration should appear inside the logic model as causal conditions for BCT enactment, rather than being represented only as external implementation context.

Current research context

The question connects directly to an active implementation programme

The current NIHR-funded evaluation of getUBetter for non-specific low back pain examines users and non-users across an Integrated Care System, interviews patients and healthcare professionals about decisions to use or stop using the app, and aims to refine programme theories about what works, for whom and under what circumstances.

That makes the distinction between logic-model specification and mechanism enactment in context empirically testable rather than purely conceptual.

Method boundary

What this note is

This is a research-development note for structural interpretation and external correction. It is not a re-analysis of getUBetter, a claim that its BCTs are not enacted, or a formal implementation evaluation.

The original studies and current implementation research remain authoritative for their methods and findings. Corrections from the study authors or relevant implementation researchers should be recorded transparently and used to revise this working interpretation.
